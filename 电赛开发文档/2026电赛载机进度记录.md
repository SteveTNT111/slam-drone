## 3. 电机输出问题判断

Pixhawk 4 是 FMUv5，官方资料说明它有 8 路来自 IO 的 PWM 输出和 8 路来自 FMU 的 PWM 输出。PX4 文档也把 `PWM_MAIN_RATE` 标为 IO，`PWM_AUX_RATE` 标为 FMU。

当前问题本质是：

```text
PX4 默认多旋翼电机输出在 MAIN / I/O PWM OUT
但实际电调信号线接到了 FMU PWM OUT / AUX
```

这不是 FAST-LIO2 或 MAVROS 问题，而是 PX4 输出端口映射问题。

## 5. PX4 上的紧急输出设置路线

### 5.1 安全前提

所有输出测试必须先做：

```text
拆桨
断开不必要负载
QGroundControl 先导出参数备份
只接 USB 时先不要接动力电池
确认分电板地线和电调信号地线可靠共地
```

PWM 电调必须有信号地。PX4 官方 PWM ESC 文档也强调，ESC servo 插头的 PWM signal 和 GND 都要接，不能只接信号线。

### 5.2 第一优先级：尝试 SYS_USE_IO=0

对 Pixhawk 4 / FMUv5 这类同时有 MAIN 和 AUX 的板子，PX4 官方 DShot 文档给出的典型方法是：

```text
SYS_USE_IO = 0
```

含义：禁用 IO PWM，让 AUX 标号的 FMU 输出按 MAIN 的用途来用。

操作建议：

1. 用 QGroundControl 连接 Pixhawk 4。
2. 参数里搜索 `SYS_USE_IO`。
3. 设为 `0`。
4. 重启飞控。
5. 让电调信号线接在 FMU OUTPUT / AUX 1-4。
6. 拆桨做电机测试，确认 AUX1-4 是否按机架电机 1-4 动作。

如果这一步成功，就不要再动 ArduPilot，也不要再改复杂 mixer。

### 5.3 如果 QGC 里能看到 Actuator / Output Function

PX4 1.13 参数参考中存在 `PWM_AUX_FUNC1` 等参数，功能值里 `101` 到 `104` 分别代表 Motor 1 到 Motor 4。

可检查但不要盲改：

```text
PWM_AUX_FUNC1 = 101  # Motor 1
PWM_AUX_FUNC2 = 102  # Motor 2
PWM_AUX_FUNC3 = 103  # Motor 3
PWM_AUX_FUNC4 = 104  # Motor 4
```

注意：PX4 1.13 的 `SYS_CTRL_ALLOC` 默认是关闭的，官方参数说明也说动态 Control Allocation 仍是 work-in-progress。电赛前夜不建议为了输出映射而贸然开启不熟悉的控制分配体系。优先走 `SYS_USE_IO=0` 这条更接近旧 mixer 的路线。

### 5.4 如果 SYS_USE_IO=0 仍不出电机

保守兜底路线按风险排序：

1. 最快机械兜底：把四根电调信号线改回分电板/飞控默认 `MAIN / I/O PWM OUT` 对应 M1-M4。
2. 其次：在 PX4 旧 mixer / airframe 文件层面改 AUX mixer，但比赛前夜不推荐。
3. 最后才考虑刷 ArduPilot。

## 10. 2026-07-28 晚：Pixhawk 4 FMU/AUX 输出问题已解决

### 10.1 现象

更换为 Pixhawk 4 / FMUv5 飞控和对应分电板后，电调信号线已经接在分电板 `FMU OUTPUT` 一侧。最初 PX4 默认电机输出没有从这些焊盘出来，导致 M1-M4 电机测试无响应。

### 10.2 处理

在 PX4 1.13.3 参数中设置：

```text
SYS_USE_IO = 0
```

重启飞控后，FMU/AUX 侧输出立刻生效。说明当前接线确实处在 Pixhawk 4 的 FMU PWM OUT / AUX 输出链路上，而不是 I/O PWM OUT / MAIN 输出链路上。

### 10.3 原理记录

Pixhawk 4 / FMUv5 同时有两组 PWM 输出：

```text
I/O PWM OUT / MAIN  -> 由 IO 协处理器输出
FMU PWM OUT / AUX   -> 由 FMU 主处理器输出
```

PX4 多旋翼机架默认通常把电机分配到 MAIN 输出。`SYS_USE_IO=0` 的作用是禁用 IO PWM，使系统走 FMU-only 输出路线，于是 AUX/FMU 侧可以按 MAIN 电机输出使用。

这个现象与 PX4 官方 Pixhawk 4 wiring 说明一致：`MAIN` 在 PX4 固件里映射到 Pixhawk 4 的 `I/O PWM OUT`，`AUX` 映射到 `FMU PWM OUT`；分电板上 `FMU PWM-IN` 内部接到 `FMU PWM-OUT`，`I/O PWM-IN` 内部接到 `M1-8`。

### 10.4 当前新问题

输出恢复后发现：

- 左前电机转向反了
- 右后电机转向反了

当前计划：使用刷 Betaflight 的飞控连接电调，进入 Betaflight Configurator / BLHeli 配置链路，对对应电调执行电机方向反转。

### 10.5 操作注意

- 继续保持拆桨。
- 只反转确认错误的两路电调，不要批量全改。
- 改完后重新做 PX4 电机测试，确认：电机编号、转向、桨叶方向三者一致。
- 电调反转完成后，再回到 PX4，不建议因此切换到 ArduPilot。


### 10.6 BLHeliSuite32 反转受阻记录

尝试使用 `BLHeliSuite32 32.10.0.0` 修改电机 3、4 的方向时，软件弹窗提示：

```text
ESC#1 seems to be a "Flycolor_Raptor_5" pre-release Rev31.x prototype sample.
It is not possible to upgrade this ESC to a release version.
```

判断：

1. 先确认 BLHeliSuite32 是否只是禁止升级，是否仍允许 `Read Setup` 后只改 `Motor Direction` 并 `Write Setup`。
2. 如果设置写入也被禁止，优先尝试 PX4 DShot 命令反转电机 3、4，前提是当前 ESC 支持 DShot，且飞控已经接在 FMU/AUX 1-4。
3. 如果软件和 DShot 命令都无法反转，再考虑最后兜底：交换对应电机任意两根三相线。

### 10.7 PX4 DShot 命令尝试记录

当前 ESC 仍工作在 PWM 模式下，在 PX4 MAVLink Shell / NSH 中执行：

```text
nsh> dshot reverse -m 3
ERROR [dshot] module not running
```

判断：

- 这个报错说明 PX4 当前没有启动 DShot 驱动模块。
- 直接原因通常是 `DSHOT_CONFIG=0`，也就是当前输出协议仍是 PWM/Oneshot。
- 如果 ESC 支持 DShot，且电调信号已经接在 FMU/AUX 1-4，则可以临时把 `DSHOT_CONFIG` 改为 `300` 或 `600`，重启后再执行 `dshot reverse/save`。
- PX4 官方参数说明：`DSHOT_CONFIG=0` 表示禁用 DShot 使用 PWM/Oneshot；`150/300/600/1200` 分别表示 DShot150/300/600/1200，并且需要重启。

赛前建议：优先从 `DSHOT_CONFIG=300` 开始，不要一上来用最高速。反转并保存电调方向后，可以再切回 PWM 模式并重新验证电机方向。

## 11. 关于 DShot、FMU/IO 分工、NuttX 的理解记录

记录时间：2026-07-28 晚。

### 11.1 当前新发现

当前电调虽然原本工作在 PWM 模式，但把 PX4 临时切到 DShot 后，飞机也可以正常输出、正常飞行，没有明显问题。也就是说，这套 `Flycolor_Raptor_5 / BLHeli32` 电调至少能够接受当前 PX4 输出的 DShot 信号。

这也解释了为什么前面可以通过 PX4 的 `dshot reverse/save` 这一路线绕开 BLHeliSuite32 的预发布固件限制，直接完成电机方向处理。

### 11.2 为什么 Pixhawk 4 上 DShot 正好和 SYS_USE_IO=0 绑定在一起

PX4 v1.13 官方 DShot 文档里说明：

- DShot 相比 PWM / OneShot，具有更低延迟、校验、更少校准需求等优点。
- DShot 可以通过命令反转电机方向，不需要物理重焊电机线。
- 对同时有 `MAIN` 和 `AUX` 的 Pixhawk，DShot 只能用在 FMU 端口，也就是标成 `AUX` 的输出。
- 因为多旋翼电机默认通常分配在 `MAIN`，所以要把 `SYS_USE_IO=0`，让 `AUX` 标号输出像 `MAIN` 一样使用。
- FMUv5，例如 Pixhawk 4，DShot 只支持前 4 个 FMU 引脚。

这和本机现象完全对应：

```text
电调接在 FMU/AUX 1-4
SYS_USE_IO=0 后输出恢复
DSHOT_CONFIG 开启后 dshot 模块能工作
Motor 3、Motor 4 可以通过 dshot reverse/save 反转
```

因此如果 DShot 模式下电机输出稳定、解锁正常、电机测试正常，当前可以继续保持 DShot，不必为了“回到旧 PWM 习惯”而强行切回 PWM。

### 11.3 为什么 Pixhawk 4 要分 FMU OUTPUT 和 IO OUTPUT

Pixhawk 系列早期架构里常见两个处理器：

```text
FMU = Flight Management Unit，主处理器
IO  = Input/Output 协处理器
```

粗略分工是：

```text
FMU：跑 PX4 主程序、姿态/位置控制、EKF、MAVLink、日志、参数、任务调度、传感器融合
IO ：处理 RC 输入、安全开关、PWM 输出、部分 failsafe / 安全相关输出
```

所以硬件接口上自然分成：

```text
MAIN / I/O PWM OUT  -> IO 协处理器侧输出
AUX  / FMU PWM OUT  -> FMU 主处理器侧输出
```

这样设计的历史原因主要有三点：

1. **早期 MCU 性能和定时器资源有限**：主处理器既要跑 EKF、控制、通信、日志，又要稳定产生多路 PWM，会增加实时负担。
2. **安全冗余**：即使 FMU 主程序异常，IO 侧仍可承担 RC 输入、安全开关、部分输出保护和 failsafe 相关逻辑。
3. **兼容传统机型**：固定翼、VTOL、舵机、云台等需要很多 PWM/舵机输出，IO 扩展输出数量更方便。

所以这个架构不是“多此一举”，而是 Pixhawk 早期为了可靠性、扩展性和兼容性做出的工程折中。

### 11.4 为什么穿越机类 F4/F7/H7 飞控通常不分 MAIN/AUX 和 FMU/IO

Betaflight / INAV / ArduPilot 兼容的很多 F4、F7、H7 小飞控通常是单主控架构：

```text
一个 STM32 主 MCU 直接处理 IMU、RC、OSD、DShot/PWM、电机输出、黑匣子等
```

这类飞控面向穿越机和小型多旋翼，典型特点是：

- 电机数量少，通常 4 到 8 路。
- 更重视低延迟 DShot 输出。
- 很少需要大量传统舵机输出。
- 硬件空间和成本压力大，不适合再放一个独立 IO 协处理器。
- F7/H7 之后主控性能、定时器、DMA 资源更强，单 MCU 已经足够完成主要输出任务。

所以它们通常没有 `MAIN/AUX` 两套输出概念，也没有 Pixhawk 这种显式 `FMU/IO` 分工。

### 11.5 为什么 newer Pixhawk / 雷迅类新飞控也逐渐弱化 IO 协处理器

大趋势确实是：很多新飞控不再强依赖独立 IO 协处理器，原因包括：

1. 新 MCU 变强：例如 F7、H7、H743/H753、甚至更高性能主控，算力、RAM、定时器、DMA 都比早期强很多。
2. DShot / UAVCAN / DroneCAN 等数字输出更普遍，不再只是传统 PWM 舵机输出。
3. 多旋翼常用输出数量不多，单主控直接出电机信号足够。
4. 板子越来越小，减少 IO 芯片可以降低成本、体积和复杂度。
5. PX4/ArduPilot 软件架构也逐渐适应无 IO 板的硬件。

但这不代表 IO 协处理器完全没价值。对大型平台、固定翼/VTOL、多舵机、多冗余、安全要求更高的载机，独立 IO 仍然有存在意义。

### 11.6 NuttX 和传统裸机程序的区别

传统裸机程序通常是：

```text
main while 循环 + 定时器中断 + 外设中断 + 手写状态机
```

优点：简单、开销小、可控；缺点是项目一复杂，就容易变成大量中断、全局变量、状态机互相缠绕。

NuttX 是 RTOS，PX4 官方文档称它是 PX4 在飞控板上运行的主要实时操作系统。它不是电脑上的 Windows/Linux，也不是单独安装到硬盘里的系统，而是和 PX4 固件一起编译、一起烧进飞控 MCU。

NuttX 提供：

```text
任务/线程
优先级调度
定时器
驱动模型
文件系统/SD 卡访问
串口/设备抽象
NSH 命令行
POSIX 风格 API
```

所以 PX4 里可以有很多模块同时运行：

```text
commander
sensors
ekf2
mc_att_control
mavlink
logger
navigator
dshot
pwm_out
```

这些模块之间通过 uORB 这类消息总线通信。相比裸机，NuttX 让大型飞控软件更像“很多任务协作的系统”，而不是一个超级 while 循环。

但 NuttX 仍然是嵌入式实时系统，不是普通桌面系统。底层仍然有中断、定时器、DMA，只是 RTOS 把任务调度和驱动组织起来了。

### 11.7 对当前电赛载机的实际结论

当前 Pixhawk 4 + PX4 1.13.3 的实际选择是：

```text
SYS_USE_IO = 0
电调接 FMU/AUX 1-4
DSHOT_CONFIG 保持可用的 DShot 档位
Motor 3、Motor 4 用 dshot reverse/save 反转
```

如果 DShot 模式下 QGC 电机测试、解锁、低油门响应都正常，就没有必要再回 PWM，也没有必要为了电调方向去动烙铁。

下一步必须做：

- [ ] 拆桨状态下确认 Motor 1-4 编号正确。
- [ ] 拆桨状态下确认 Motor 1-4 旋向正确。
- [ ] 确认 DShot 模式下所有电机低油门启动一致。
- [ ] 确认没有混用 FMU 上的 DShot 和 PWM 输出。
- [ ] 再进入 PX4 自稳/定点/SLAM 链路测试。
